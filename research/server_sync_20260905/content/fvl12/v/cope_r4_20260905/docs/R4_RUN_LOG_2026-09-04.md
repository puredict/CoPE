# R4 第一轮修改与复跑记录

本次按照用户提供的修订建议分两轮处理。第一轮修复接口、状态校验、运行记录和预算诊断；第二轮的 Generic Patch、不同恢复目标、多订单因果变化和动作边界物理闭环尚未实现。此记录中的开发结果不作为论文确认性测试结果。

## 已完成的代码修改

1. 提示词、输出 schema 和执行器共用规范操作定义。输入事件 `override_current` 对应输出操作 `override`。四类固定开发示例覆盖 `suspend`、`restore`、`override` 和 `restore_root`。
2. CoPE 和 FSR-PC 均使用静态结构化生成约束；schema 不接收当前事件，不把正确操作或目标固定为唯一答案。
3. 用独立的字典状态转换实现作语义诊断，不再调用 CoPE 的核心更新函数生成 FSR 参考答案。结构合法但语义错误的候选仍由该方法提交并计错，不用 oracle 修复。
4. 增加事务深拷贝、失败回滚、过期 revision、嵌套谱系、完整历史和 continuation 的性质测试。已完成动作的精确前缀过滤仅是单元级后缀编译验证，尚未构成真实动作中断闭环。
5. 客户端保留流式部分文本、服务报告的实际 tokens、TTFT、请求 ID、绝对超时和取消状态。关闭连接不等于已确认服务端停止；下一请求前检查服务队列。
6. 逐事件保存结果与状态，区分生成失败、schema/转换拒绝、语义错误和已提交错误。未进入物理阶段时 `physical_success=null`；符号执行成功另列，不记作真实端到端成功。
7. 新 runner 区分 `reference_diagnostic` 与 `free_running`。前者仅允许开发集和非物理诊断；后者始终使用本方法实际提交的状态。未完成开发验收与充分预算冻结前，正式测试集被锁定。

## 真实 tokenizer 初步测量

使用已有 Qwen3-32B snapshot `9216db5781bf21249d130ec9da846c4624c16137` 的 tokenizer 和 chat template，`enable_thinking=false`。开发 seeds 为 1000、1001，共 116 条方法--事件记录。下表是特定合法参考序列化的长度范围，不是所有合法答案的数学最小值。

| Profile | 事件数 | FSR 紧凑参考 tokens | FSR 排版参考 tokens |
|---|---:|---:|---:|
| calibration：8 slots、深度 2 | 7 | 1557--2372 | 2411--3666 |
| lineage_valid：10 slots、深度 6 | 11 | 2036--4144 | 3130--6382 |
| long_lineage：48 slots、深度 6 | 11 | 11107--13223 | 16761--20021 |

全体最长完整 prompt 为 15565 tokens。按预先写入配置的“最大参考输出加 15% 余量并向上取整到 1024”规则，充分预算的统一输出上限候选为 23552 tokens；timeout 仍须来自同一服务下的实测暖机吞吐。原 4096 tokens / 90 秒条件保留。

这支持一个明确但有限的判断：48 slots 条件下，本次所有紧凑参考全文均超出 4096 输出预算，因而固定预算结果包含显著序列化容量限制；不能仅据此归因于模型不理解恢复关系。

## 服务器与产物隔离

- 推理：fvl10，复用既有离线模型和环境，只使用启动前确认为空闲的 GPU 0--3，TP=4，bfloat16，单并发。
- R4 服务与输出：`/mnt/data_new/lijingsu_cope_r4_20260905/`。
- 物理执行环境：fvl12 原有 LIBERO / MuJoCo 环境，CPU OSMesa，geometry-oracle OSC_POSE 控制器；不使用他人 GPU。
- R3 实验输出保留，没有覆盖、删除或复用其运行目录。

第一次 R4 服务启动尝试采用 49152 上限，被模型配置的原生 `max_position_embeddings=40960` 拒绝。没有采用强制外推开关。第二次改为原生 40960；预估最大 prompt 加统一输出预算为约 39117，最终冻结时还须对实际充分预算 prompt 重新计数。

`capacity_initial` 是服务启动前、假设较大上下文的规划审计，其中上下文字段不代表已成功启动的服务器。最终结论必须引用与实际服务一致的后续容量审计。

## 实时运行状态

本地验证目前为 R4 43 项、新旧合计 51 项通过。开发 seed 1000 的独立本地参考七事件加真实 LIBERO 执行 smoke 已通过；该项使用确定性 oracle，绝不是模型实验成功或真实模型吞吐数据。

第一次实时请求接入检查中，四个调用均在生成之前被 V1 服务拒绝：请求指定 xgrammar，但服务启动时仍为 auto。原始目录 `cope_r4_dev_fixed_cal_1000_20260905` 与 `cope_r4_dev_fixed_long_1000_20260905` 完整保留，这四个基础设施接入失败不会冒充方法性能测量。随后停止本人的该服务，并将引擎启动 backend 与请求 backend 显式对齐；复跑必须使用新目录。

随后发现该版本 CLI 只接受基础 backend 名称，尽管内部组件接受冒号选项。第三次启动在参数解析时退出。第四次服务采用 CLI 明确支持的 `xgrammar`，客户端也使用完全一致的字符串。V1 的显式 xgrammar 路径不回退到其他后端；任意空白仍被允许，紧凑格式由同一条提示词要求，不声称已通过 grammar 强制压缩。

### 实际模型：固定预算 CoPE，开发 seed 1000

`cope_r4_dev_fixed_cal_1000_v2_20260905` 中的 CoPE 已完成全部七次真实模型调用，原始操作依次为 `suspend, restore, override, override, suspend, restore, restore_root`，全部合法且与独立参考一致。总模型调用耗时 37.179 秒，输出共 636 tokens；这不是含仿真在内的端到端耗时。

直接核验八份状态快照，确认 revision 0--7 连续、前后指纹连续、没有 reference-fed 重置；根为 active，两层 detour 为 expired，父子边及深度 0/1/2 正确。根原始 payload 保留，最终 plan 为 butter→B、milk→A、yogurt→A；七个未涉及的 archive/safety 记录在全部快照中不变。三个 workflow 的最终历史长度分别为 5、3、4，事件序号和模式转换均正确。

该条 CoPE 的真实 LIBERO 物理执行也已完成：`physical_attempted=true`、`physical_success=true`、`end_to_end_success=true`。同一服务下的长条件 CoPE 也完成 11 次更新与物理任务，总输出 1419 tokens、模型调用耗时 137.576 秒；独立完整 gold 轨迹审计全部匹配。单条开发路径不能作为多场景恢复可靠性或论文贡献的充分证据。

### xgrammar 运行成本诊断与配置修正

小条件 FSR 前两步均正确，分别为 1579 tokens / 66.268 秒、1617 tokens / 84.922 秒；第三步在 90 秒超时，保留 1585 个服务报告的部分 tokens。服务队列在断开后第 1 秒观测到 running=waiting=0，未让残余生成与下一请求重叠。长条件 FSR 第一步也在 90 秒超时，收到 1648 个 tokens。

这三份小条件 FSR 文本没有字符串外空白膨胀。CPU 重放正常文本，复现了 xgrammar token-mask 成本随生成位置增长的现象；限制空白和收窄 payload 的只读对照都未消除该增长，因此没有修改 schema 的状态表达范围。

相同的完整 FSR 原始文本在已安装的 guidance 后端上通过 CPU 重放，未出现同样的尾部增长；两种方法均通过该后端的 schema / Processor 接口检查。具体测量、可比性限制见 `FSR_CPU_GRAMMAR_DIAGNOSTIC.md` 与 `guidance_backend_gate.md`。这些 CPU 测量不是实际模型加速结果。

第五次服务统一改为 `guidance`，模型、精度、TP、上下文、原始 schema 与预算不变。新目录使用 `cope_r4_dev_guidance_...` 前缀；客户端与服务端 backend 显式一致。充分预算必须只使用 guidance 的开发测量，collector 与容量冻结器会拒绝混用其他 backend 数据。实时 guidance 结果仍待补充。
